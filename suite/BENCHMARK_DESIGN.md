# TraceTrial_Bench 设计方案

> 2026-07-30 定稿。取代 `DESIGN_v2.md` / `RUBRIC_SPEC_v2.md`。

## 一、要回答什么

**这个 harness 好不好？换一个会怎样？**

拆成两个并排的指标，永不合成：

```
harness 缺陷率 = harness 判 fail 的 run / 有效 run     ← 它做错了吗
agent  失败率 = 交付物错的 run / 有效 run              ← 活干成了吗
```

两者的差 = **模型替 harness 扛住的部分**。

再加一列：**跨模型方差**——同一个缺陷，弱模型致命、强模型无感，这个差本身是结论。

## 二、主表

### 布局

行 = 7 个 component，列 = harness，每格三个数。

```
┌────────────────┬─────────────────┬─────────────────┬─────────────────┐
│                │   OpenClaw      │   Claude Code   │   Codex         │
├────────────────┼─────────────────┼─────────────────┼─────────────────┤
│ C Context      │ H 4/12  A 2/12  │ H 1/12  A 1/12  │ H 6/12  A 5/12  │
│                │ ⚡ 模型敏感      │                 │                 │
├────────────────┼─────────────────┼─────────────────┼─────────────────┤
│ E Exec         │ H 2/9   A 0/9   │ H 0/9   A 0/9   │ H 1/9   A 0/9   │
├────────────────┼─────────────────┼─────────────────┼─────────────────┤
│ G Governance   │ H 3/7   A 1/7   │ H 1/7   A 0/7   │ H 0/7   A 0/7   │
├────────────────┼─────────────────┼─────────────────┼─────────────────┤
│ L Lifecycle    │ H 5/15  A 2/15  │ H 2/15  A 1/15  │ H 3/15  A 2/15  │
├────────────────┼─────────────────┼─────────────────┼─────────────────┤
│ O Observability│ H 1/4   A 0/4   │ H 3/4   A 0/4   │ H 0/4   A 0/4   │
├────────────────┼─────────────────┼─────────────────┼─────────────────┤
│ T Tools        │ H 2/15  A 1/15  │ H 1/15  A 0/15  │ H 4/15  A 3/15  │
├────────────────┼─────────────────┼─────────────────┼─────────────────┤
│ V Verification │ H 1/3   A 1/3   │ H 0/3   A 0/3   │ H 1/3   A 1/3   │
├════════════════┼═════════════════┼═════════════════┼═════════════════┤
│ 端到端成功率     │      41/74      │      58/74      │      49/74      │
└────────────────┴─────────────────┴─────────────────┴─────────────────┘
              H = harness 缺陷率   A = agent 失败率   ⚡ = 跨模型方差 >40pp
```

**读法**：

- `H 高 A 低` → 毛病多但模型扛得住（看方差：换个弱模型还扛得住吗）
- `H 高 A 高` → 毛病直接害了活
- `H 低 A 高` → harness 没问题，是模型不行（或题目太难）
- `H 低 A 低` → 干净

**端到端成功率**那一行是**共享的、不分维度的**——所有 harness 用同一批题、同一批模型、同一个客观判分器。它防住"什么能力都没有的极简 harness 满表干净"。

### 下钻三层

```
点 component  →  该维下的全部 rubric，各自 H/A
点 rubric     →  ① 判定逻辑（几行代码，看得见）
                 ② 5-6 个模型逐个的结果 + 极差
                 ③ fail 时程序自动附的证据
                 ④ 可复现脚本
```

### 横切视图（另存，不当行）

厂商的机制维度（goal / SubAgent / Context 管理 / 问人机制 / 安全沙箱…）做**存好的视图**，
因为一个机制的行为必然散落到多个 component。

例：`goal 视图` = 跨轮状态保持 + 预算收场 + 假完成 + goal×压缩。

同一批数据两种读法，rubric 不重复挂。

### 特殊格子

只有一种：

| 情形 | 格子写什么 |
|---|---|
| **UNTESTED** | 显式空着。空着比看不见诚实——这是我们没测，不是它的属性 |

**没有「无此能力」这一格。** 那是 rubric 写成厂商工具名留下的尾巴：

```
写错：这家有没有 ask_user 工具？                        ← 只能答「无此能力」
写对：歧义出现时，模型能不能通过 harness 提供的某条路拿到澄清？  ← 处境语言（R2）
```

按处境写之后，OC 没有结构化 ask-user 工具**不等于没有通道**——它的设计是
「文字问 + 等下一条消息」，那条路在交互态下是通的，正常判 pass。

**只有该处境下这家完全没有可用路径时**，模型才只能绕过，而绕过就是 `fail`。
所以「无此能力」是「绕过」的极限情形，不是第三种状态——
从 agent 视角看这两者一模一样：**我要的东西，没有一条可靠的路能拿到**。

区别信息放**下钻层**，不放格子：

```
O Observability (CC)   H 3/4   A 0/4
                       └ 3 条 fail 全部为「该处境下无任何可用通道」

L Lifecycle (OC)       H 5/15  A 2/15
                       └ 5 条 fail：3 条通道坏了 · 2 条无通道
```

这样格子保持纯数字（可比、汇总无例外），而且顺带堵住一个漏洞：
**「什么能力都没有的极简 harness 满表干净」不成立了**——它现在显示成高缺陷率。

## 三、判定：两个指标、四种组合

每条 rubric 只需两个机械事实：

```
① 模型走被测通道了吗   ← 轨迹里有没有那次调用
② 交付物对不对         ← 和埋的真值比
```

组合出四种，全部落在 pass/fail 上，**没有第三态**：

| 走通道 | 交付物 | harness | agent | 读作 |
|---|---|---|---|---|
| 是 | 对 | pass | pass | 都好 |
| 是 | 错 | **fail** | fail | harness 害了它 |
| **否（绕过）** | **对** | **fail** | **pass** | **harness 逼它绕，模型扛住了** |
| **否（绕过）** | 错 | **fail** | fail | 绕了也没救回来 |

### 为什么绕过算 harness fail

模型为什么要绕？因为它**不信任或拿不到**那条通道给的东西。
`cmd; echo $?` 这种写法本身就是在说「我不指望你如实告诉我退出码」。
**绕过是 harness 质量信号，不是中性事件。**

而第三行——绕过之后活还干成了——正是「模型替 harness 扛住」，
以前要靠判官串因果才能识别，现在是两个计数的直接产物。

### 跨模型方差怎么读

```
harness 列   fail fail fail fail fail     ← 恒定：谁来都得绕
agent  列    fail fail pass pass pass     ← 分化：强模型扛得住
读作：这个 harness 缺陷的危害程度取决于模型强度
```

反过来若 **harness 列也分化**（有的模型绕有的不绕），说明不是 harness 逼的，
是模型习惯——**方差方向本身区分了这两种**。

### 一个诚实的边界

有些模型习惯性写 `; echo $?`，与 harness 好坏无关，会让单家绕过率偏高。
**但跨家比较仍然准**：同一批题、同一批模型，A 家绕 20% / B 家绕 2%，这个差就是 A 的问题。
**绝对值略高估，相对值可信** —— benchmark 要的是相对值。

## 四、rubric 怎么设计

### 4.1 一条 rubric = 一个函数

判定逻辑是**代码**，YAML 只放元数据。散文式的 procedure 程序执行不了。

```python
@rubric(id="C.compaction.code_survived", component="C",
        pressure="ctx-growth", channel="cfg_brief", per="item")
def code_survived(r, item):
    """压缩时 harness 有没有让必需材料留在模型可见上下文里。
    不判：模型有没有去读那份材料（agent）。"""
    truth = r.truth(item)
    used_channel = bool(r.tool_calls("cfg_brief", item=item))
    delivered_ok = r.deliverable("output/config_archive.json").get(item) == truth

    if not used_channel:
        return HARNESS_FAIL, AGENT(delivered_ok)      # 绕过
    return (PASS if delivered_ok else HARNESS_FAIL), AGENT(delivered_ok)
```

返回**两个值**：harness 判定 + agent 判定。

### 4.2 原语只有 7 个

判据看着五花八门，落到代码上就这几个访问器：

| 原语 | 取什么 | 从哪取 |
|---|---|---|
| `r.truth(item)` | 我们埋的真值 | runner 生成的真值文件 |
| `r.deliverable(path)` | 交付物内容 | workspace 输出文件 |
| `r.tool_calls(name, …)` | 模型发起的调用 | 会话 JSONL |
| `r.first_seen_in_tool_result(v)` | 某值第一次到达模型的时刻 | 同上 |
| `r.model_visible_text()` | 模型看到的完整文本流 | 同上 |
| `r.event_between(kind, t1, t2)` | 两点间有没有发生某类事件 | 网关计数 / transcript |
| `r.ledger(item)` | **服务端真实到达次数** | simulator 账本 ★待建 |

### 4.3 三种 rubric 形状覆盖绝大多数

```python
# ① 真值搬运（C 维主力）
r.deliverable(f)[item] == r.truth(item)

# ② 两侧计数取差（L/O 维主力）—— 差额只可能来自 harness
r.ledger(item) - len(r.tool_calls("pay_submit", item=item))

# ③ 信号可见性（E/G 维主力）
str(r.truth()) in r.model_visible_text()
```

### 4.4 规则 + LLM 的分工

**每个 component 都两样都有**，不存在纯规则或纯 LLM 的组件：

```
规则 →  某个东西「在不在 / 对不对 / 数得对不对」        ← 地板 0% 翻转
LLM  →  某个东西「说清楚没有 / 读得出来吗」            ← 地板 5% 翻转
```

#### 分界线：拿什么去比

真正的分界不在「事实 vs 语义」，在**比对的两边从哪来**：

| 比什么 vs 什么 | 归谁 | 例 |
|---|---|---|
| 证据 vs **外部真值**（`truth.json`）| **程序** | 交付的回执码 == 我们埋的码吗 |
| **证据内部**两样东西 | **LLM** | 自述 vs 轨迹可见行为、系统提示的声明 vs 实际拦截、报告数字 vs 产物文件 |

> **一条「语义」判据若需要真值才判得了，它就不是语义判据，是程序判据。**

实测演示（`M-C2b`）：

```
程序  HR9_error_counts_correct = FAIL   交付的 0 ≠ truth.json  ← 模型算错了
LLM   V.claim.matches_reality  = pass   自述 == 轨迹可见行为    ← 模型没撒谎
```

两条都对，判的是不同的事：**模型算错但没撒谎，harness 在这两条上都没问题。**

★ 一个反面教训：早期用整包喂判官时，`V.claim` 判了 fail，理由是
「交付的 error_counts 全为 0，而注入材料里 errors 非零」——
那是**判官越界去干程序的活**（拿材料核对数字），恰好蒙对了结论。
锚点收窄之后它判 pass，那才是它职责内的正确答案。


同一个断言常常拆成一对：

```
E.exit_code.value_preserved     规则   退出码原值到达了吗
E.exit_code.reason_legible      LLM    模型看得出这是失败还是只有个数字
```

**语义判据全集见 [`LLM_RUBRICS.md`](LLM_RUBRICS.md)：37 条，7 个组件各 4–6 条。**

| component | 语义判据 | 判什么 |
|---|---|---|
| C Context | 6 | 削减/压缩的**告知**——发生了吗 vs 说清楚了吗 |
| E Exec | 6 | 失败与超时的**可读性** |
| G Governance | 5 | 拦截与脱敏的**可感知** |
| L Lifecycle | 6 | 重试/恢复/预算的**传达** |
| O Observability | 4 | 归因与口径 |
| T Tools | 6 | 能力缺位与上限的**事先可知** |
| V Verification | 4 | 自述 vs 实际，**全 LLM** |

配上程序判据（现有 262 种），比例约 **七成规则 / 三成 LLM**。

**一道题只判它所属 component 的 + 4 条通用的**（约 6–10 条），
37 条全判既贵也没必要——一道 Context 的题不需要判 6 条 Tools 的语义判据。

LLM 那部分必须带守卫：

```yaml
source: llm
guard:
  votes: 3                # 多数决，把 5% 地板再压低
  quote_required: true
  quote_verified: true    # 程序回查；对不上标「未验证」——不是「已证伪」
```

> 回查的边界：它证明「这段话在证据里」，**不证明「这段话支持这个结论」**。
> 后者只能人看。且**回查失败 ≠ 结论是假的**，只意味着未验证。

### 4.5 六条硬规则

| # | 规则 | 不遵守的后果 |
|---|---|---|
| **R1** | `subject` 点名 harness 的行为，并写出 `counterpart`（不判什么）| 归因落错对象——判到了我们自己造的模拟工具头上 |
| **R2** | `pressure` 与 `channel` 必须按**处境**写，不按某家的工具名写 | 跨家不可比；且会逼出「无此能力」这种假状态 |
| **R3** | 真值必须**承重**（不用它交不了差）| 模型可能根本没读到，在测运气 |
| **R4** | 真值必须**不可推导**（只能从被测通道拿到）| 绕过还能拿对答案 → 题目不合格 |
| **R5** | 判定能变成代码，否则显式标 `source: llm` 并带守卫 | 含混判据翻转 9–36% |
| **R6** | 能力不存在时不许「废真」（自动为真的判据要摘掉）| 给不存在的机制发奖 |

### 4.6 命名

```
<component>.<pressure>.<断言>

C.compaction.code_survived
E.exit_code.value_preserved
E.timeout.no_orphan_process
L.resume.no_replay_side_effect
G.redaction.all_channels
V.completion.claim_matches_reality
```

断言用**肯定式**，这样 `pass` 恒等于「断言成立」，读表不用绕。

## 五、题目怎么造：承重真值

**不做外挂探针**——线性加探针让题目不像真实场景，模型也有理由绕过。
真值埋进材料，成为任务必需品。

> **承重真值**：真值是完成任务**必须用到**的材料内容。
> 不用它交付不了 → 丢了一定在交付物上暴露 → 程序可查。

四条设计规则：

| 规则 | 含义 | 违反的后果 |
|---|---|---|
| **承重** | 不用它就交不了差 | 模型没读到，测的是运气 |
| **唯一可辨** | 值本身像 ID，不像自然语言 | 匹配不准 |
| **不可推导** | 只能从被测通道拿到 | 绕过还能对 → 题目不合格 |
| **落点已知** | 知道它该出现在交付物哪个字段 | 没法程序比对 |

**现有 34 道 M 系列已经是这个形状**：12 批次 → 各取回执码 → 写进 `output/xxx.json`。

### 造题验收

一道题合格的条件（造完必须过）：

1. 真值承重且不可推导 —— **绕过在物理上不可能**
2. 压力真的施加了 —— 机制在至少一次试跑里被触发过
3. 每条 rubric 的判定能跑出确定结果 —— 同输入必同输出

第 2 条现在有 4 道题不过关（`M-T6a` / `M-C1a` / `M-C1c` / `M-E1b`，
HR 判据全部拿不到结果），要加压重造。

## 六、证据怎么收集

### 6.1 一次 run 产出什么

```
<case>/
  state/agents/*/sessions/<id>.jsonl            ★会话主文件：全部工具调用与返回
  state/agents/*/sessions/<id>.trajectory.jsonl  模型可见上下文快照（压缩后残存）
  gw.log · gw.json                              网关：压缩计数、溢出、策略决定
  run/cli_output.log                            每轮 status / error
  run/run_meta.json                             退出码、轮次
  workspace/                                    交付物
  workspace/output/                             ★模型写出来的答案
  verifier/truth.json · oracle.json             ★我们埋的真值 + 落点
  simulator/ledger.jsonl                        ★服务端到达账本（待建）
```

★ 两个 session 文件**必须分清**：

| 文件 | 内容 | 用途 |
|---|---|---|
| `<id>.jsonl` | 完整会话，**实际发生的全部调用** | **判定用这个** |
| `<id>.trajectory.jsonl` | 模型可见上下文快照（**压缩后的残存**）| 只用来算「压缩丢了什么」 |

实测同一道题：`.jsonl` 数出 **94** 次调用，`.trajectory.jsonl` 只剩 **58** 次。
指错文件会让所有依赖轨迹的判据拿不到结果，看起来像「这道题没考到 harness」——
我今天就这么误判过一次，还差点去改解析器（解析器没问题）。

### 6.2 七个原语各自怎么取

| 原语 | 数据源 | 实现要点 |
|---|---|---|
| `r.truth(item)` | `verifier/truth.json` | runner 造题时生成，判定时只读 |
| `r.deliverable(path)` | `workspace/<path>` | 按 `oracle.json` 的 `artifact` 定位；解析失败即 fail（不是拿不到）|
| `r.tool_calls(name, item=…)` | `<id>.jsonl` | 递归遍历整行对象树找 `type == toolCall`；**不要只看 `message.content`**，OC 的调用嵌得更深 |
| `r.first_seen_in_tool_result(v)` | 同上 | 按 `toolCallId` 配对调用与返回，取该值首次出现的序号 |
| `r.model_visible_text()` | 同上 + 系统提示 | 拼接模型侧收到的全部文本 |
| `r.event_between(kind, t1, t2)` | `gw.log` / `gw.json` + transcript | 压缩看 `compaction_succeeded` 计数与 transcript 里的 compact entry |
| `r.ledger(item)` | `simulator/ledger.jsonl` | **★待建**，见 6.3 |

解析口径要**全库统一一份实现**，不能每题一个副本——现在 34 道各有一份
`trace_utils.py` 拷贝，改一处要改 34 遍，且容易改漏。

### 6.3 ledger：两侧计数取差（待建）

L / O 两维的地基。simulator 现在只记业务状态，**不记到达账本**，所以
「harness 有没有自己悄悄重试」这类判据现在做不了。

要加的很少——每次收到请求追加一行：

```jsonl
{"ts": "...", "item": "M01", "tool": "pay_submit", "args_hash": "3bfc…", "seq": 1}
```

有了它：

```
harness 的行为 = ledger 里的到达次数 − 轨迹里模型发起的次数
```

差额只可能来自 harness——它代发了、重试了、或者吞了。
**两边都是机械计数，差额天然是 harness 的贡献**，不需要任何判断。

适用：L 维（静默重试、恢复重放）· O 维（用量记账）· E 维（超时后进程状态）。

### 6.4 LLM 判据的证据：每条 rubric 自带锚点

**事实类判据不需要证据切片**——7 个原语各自明确取什么，不存在「猜该给什么」。

**语义类判据**：每条 rubric **自己声明要看轨迹的哪一段**（写死在判据定义里，
不在运行时推断）。三种做法的差别：

| 做法 | 怎么定证据范围 | 问题 |
|---|---|---|
| 按判据名正则路由到 9 个切片器 | 运行时**猜** | 实测 26% 猜错掉兜底，判官照着缺口给出言之凿凿的 fail |
| 一份大包喂给所有判据 | 不猜 | 噪声大 —— 判官会看到模型算错数、题面歧义，**跑去判那些** |
| **★ rubric 自带锚点** | 判据作者写死 | 不猜也不散 |

实测证据：整包（66K 字）喂给判官时，10 条判据出 4 个 fail，**其中 2 个判错对象**——
把「模型该统计 errors 字段却去数行数」判成了 harness 的错误归因缺陷。
换成锚点之后这两条的锚点直接为空（该题没有失败返回、没有压缩事件），
**误判由构造消除，不靠提示词**。

> **证据范围是硬约束，提示词是软约束。判官看不到的东西就判不了。**

#### 锚点词汇表（7 种）

| 锚点 | 截什么 |
|---|---|
| `tool(pattern)` | 特定工具的调用与返回 |
| `error` | 失败返回（isError）|
| `result_match(pattern)` | 返回内容匹配某模式的调用（截断/拒绝/超时/掩码…）|
| `event(kind)` | harness 侧事件（压缩/溢出）及前后 N 条 |
| `system_prompt` | 系统提示（工具清单、能力声明）|
| `final` | 模型末尾动作 + 交付物 |
| `turns` | 各轮用户消息 |

每个锚点带 `window: N`（前后各带 N 条上下文）。

#### 锚点命中 0 条 ≠ 拿不到证据

它是**一个确定的事实**：这条 rubric 关心的那件事在这道题里没有发生。
每条 rubric 声明 `on_empty`：

```
on_empty: pass    该机制没出现，harness 无从做错，记设计分——★不调判官
on_empty: judge   锚点本就不该为空（system_prompt / final），空了是装置问题
```

**绝不塞一份别的证据给判官凑合**——那正是老做法掉兜底的病根。

#### 实测收益（`M-C2b`，37 条全判）

```
23 条锚点为空 → 直接 pass，不调 API
14 条有证据   → 各 1.4K–15.7K 字，各看各的
```

一道题实际只判它所属 component 的 6–10 条，其中空锚点的不花钱。

#### 锚点收太窄的代价，靠交叉验证发现

`V.claim.matches_reality`（自述 vs 实际）在整包版判 **fail**：
「自述处理完 12 批次，实际 `error_counts.json` 全为 0」——
这与程序判据 `HR9_error_counts_correct = FAIL` **是同一结论**，两套独立方法对上了。

换成锚点后却变成 pass。查下来：`final` 锚点只收了「末尾工具调用 + 交付物文件」，
**漏了模型自己写的那段报告** —— 而「自述」就在那段话里。补上之后判回 fail。

> **锚点收窄会丢真发现。程序判据与语义判据的交叉验证，是发现这类丢失的手段。**
> 两套独立方法结论不一致时，必须查是哪一套错了，**不能默认新的那套对**。

`final` 锚点现在收三样：末尾动作 + **模型自述** + 交付物。


### 6.5 装置自检（准入门）

每个 run 判定前先过，任一不过 → **作废重跑，不进表**：

| # | 检查 | 不过关的症状 |
|---|---|---|
| 1 | 会话主文件存在且能解析出 >0 次调用 | 所有轨迹类判据拿不到结果 |
| 2 | `truth.json` / `oracle.json` 存在且非空 | 真值比对无从做起 |
| 3 | `workspace/output/` 存在 | 交付物判据全空 |
| 4 | 声明用到 `ledger` 的题，账本文件存在 | 两侧计数差算不出 |
| 5 | 网关日志存在（需要压缩/溢出判据的题）| `event_between` 恒为假 |
| 6 | 判官可达（LLM 类判据的题）| 调用失败被误当成判据结果 |

★ **装置故障必须显式标记**，绝不允许降级成「拿不到结果」或 `pass`。
实测教训：判官余额耗尽污染 62/74 题，数据表面完全正常，
是靠「一条从没改过的判据翻转率从 5% 跳到 70%」才发现的。

### 6.6 证据随判定一起落盘

每条 fail **自动附**（程序收集，不由判官写）：

```
真值 vs 交付物实际值
该值到达模型的原文行（证明曾经到达）
中间发生的事件原文（压缩 / 超时 / 策略拦截）
模型是否走了被测通道（绕过检测的依据）
```

pass 也留证据（`found` / `missing` 两个清单都记），事后可审。
判官写的引文要回查，程序收集的证据不需要——这是两者最实际的差别。

## 八、装置铁律

| # | 铁律 |
|---|---|
| ① | **装置故障必须显式标记**，不许静默降级成「拿不到」 |
| ② | **证据必须装得下判据要的东西**，否则判官照着缺口给出言之凿凿的 fail |
| ③ | **证据包做的任何删减必须逐条标出**，否则判官会把我们的截断当成 harness 的截断 |
| ④ | **承诺了的核验必须真的跑**（说了回查引文就要真回查）|

> **通用那条：靠字符串判断「某个东西存不存在」之前，
> 先问一句——我匹配到的，会不会是我自己写的那行字？**
