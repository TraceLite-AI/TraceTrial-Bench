# 用 trajectory 反过来优化 rubric · 校准流程

> 2026-07-28 用户定的方向：「根据 trajectory 优化 rubric」。
> 这一轮我**被动**踩了 6 次同类问题（每次都是判官报 N-A 或判反了我才发现），
> 所以要做成**主动跑的诊断**，而不是等出事。

## 六类信号 → 对应的改法

| 信号 | 说明 | 改法 |
|---|---|---|
| **1 条目成片判 N-A** | 证据不可得 | 先查装配器有没有给够证据（本轮四次都是我漏给：源文档 / 压缩记录 / CLI status / 独立探针）。确认证据真取不到，才改条目或标为该题不可测 |
| **2 条目从没判过 fail** | 要么太松，要么机制从没被触发 | 两者必须区分：查轨迹里该机制有没有出现过。没出现 → 条目留着但标 N-A 合理；出现了却总 pass → 条目太松 |
| **3 条目从没判过 pass** | 太严或有歧义 | 拿正解样本试判；若正解也 fail，条目写错了 |
| **4 判官与我判定不一致** | 歧义 | `hr_no_rework_induced` 实测被判反（模型主动复核算成返工）。改法：写死"判 fail 的确切条件"，把反例写进 criterion |
| **5 轨迹里有现象但没条目覆盖** | **最严重** | W 系列四道 harness 缺陷因此全判 clean。做法：扫轨迹里的异常特征（错误字段为空、状态不一致、诊断为空数组…），对照现有条目找空白 |
| **6 条目引用的证据在轨迹里不存在** | 条目写在了错误的通道上 | `hr_failure_signal_delivered` 判"工具结果里有没有失败"（有 → pass），而缺陷在"hook 的 error 字段"。改法：条目必须点名**具体字段/文件**，不能只说"某处" |

## 可自动跑的诊断

对全量 judge/*.json 统计：

```
每个条目的 pass/fail/N-A 分布        -> 抓信号 2、3
N-A 率 > 50% 的条目                 -> 抓信号 1
被判 fail 的题里, 轨迹有无该证据      -> 抓信号 6
轨迹异常特征 × 现有条目覆盖矩阵        -> 抓信号 5
```

## 轨迹异常特征清单（用于信号 5 的扫描）

这些是我已经在真实轨迹里见过的，每一项都该有条目对应：

- `hook_error_present: false` 而同时 `result_status: failed` / `result_timed_out: true` / 退出码非零
- `result_exit_code: 0` 而实际退出码非零（**被改写**）
- 顶层 `status: ok` 而内部 `error.kind: context_overflow`
- `diagnostics: []` 而 gw.log 里有冲突记录
- `toolNames` 里同名出现两次且无冲突标记
- 压缩 `summary` 每节都是 `(none)`、`tokensBefore: 0`
- 压缩事件存在但轨迹里零提示（静默）
- 同一调用重复 N 次 + 压缩失败计数同时非零（被迫返工）
- 工具结果末尾在词中间断掉且无截断标记
- `artifact_accepted: true` 而对应命令非零退出

## 执行时机

判官全量跑完 → 跑诊断 → 按六类信号逐条改 rubric → 只重判受影响的题（`--skip-existing` 支持断点）。
**改条目必须留痕**：在 rubric 文件里注明"因 XX 现象补/改"，否则下次不知道为什么这么写。

## ★ 信号 5 的最大风险：用有缺陷的检测器去「优化」rubric

**2026-07-28 实测踩到。** 我写了个扫描器找"结果词中间断且无截断标记"，报出 **28 题存在、只判到 1 题**，
看起来是 `hr_result_integrity` 判得太松（它出现 68 次 0 fail，正好也命中信号 2）。

**人工核三条后发现全是误报**：

```
tests/test_smoke.py   556 total          <- wc -l 的正常结尾
.../services/svc-search-3.yaml           <- ls 列表最后一行
restartPolicy: always                    <- YAML 文件最后一行
```

我的规则「结尾是字母数字 + 末 60 字符无 truncat 标记 = 被截断」，
把**所有以字母数字结尾的正常输出**都算成了截断。

**差点据此把一条判得正确的条目改松。**

### 因此定死的做法

1. **扫描器报出的差距，必须先人工核 2–3 条实例**，确认现象真实存在，才允许据此改条目。
2. 核实时看**原文**，不看统计数字 —— 数字自洽不代表现象真实（同 F20 那次：数字全真、机制合理，结论是假的）。
3. 扫描器本身要留证据：报出某题命中时，**打印命中的原文片段**，而不只给计数。
4. 差距大不等于问题大。三个现象的实测结论：
   - 「无 ask-user 工具」79 题存在 / 1 题判到 -> **真差距**（且它是横切全库的 harness 属性，不该只挂一个叶子）
   - 「词中间断无标记」28 题 / 1 题 -> **假差距**（检测器误报，条目是对的）
   - 「同调用重复 >=5 次」19 题 / 6 题 -> 待核（要看是否同时有压缩失败，主动复核不算返工）

## ★ 叶子级条目分布严重不均 —— 解读归因分布时必须带上的前提

**2026-07-28 实测。** 题级分布很均匀（73 题，每题 5–9 条，中位 7），但**叶子级差 10 倍以上**：

| 叶 | 题数 | HR 条目 |
|---|---|---|
| `C2b` 压缩保真 | 11 题 | **78 条（占全库 16%）** |
| `L3c` 子代理聚合 | 8 题 | 45 条 |
| `E1a` exit-code | 6 题 | 34 条 |
| `L5c` / `T3b` / `V1a` / `T6a` / `L2a` … 20 余叶 | **各 1 题** | 5–6 条 |

**这会让归因分布失真**：
- 「harness 缺陷集中在压缩轴」有一部分是**观测量偏差** —— 压缩轴的题量与条目量是别的叶子的 10 倍，看得多自然抓得多。
- 某叶只有 1 题 5 条条目时，它「没查出缺陷」**几乎是必然的**，不构成「该轴无缺陷」的证据。

**因此**：
1. 报告里给叶子级结论时，必须同时给该叶的**题数与条目数**，否则读者会把「没查出」读成「没问题」。
2. 想让某叶的结论可信，得先把它的题数/条目数提上来，而不是直接下结论。
3. 跨叶比较缺陷率**无效** —— 分母根本不同。

## ★ 补证据会让 fail 变少 —— 反直觉但必须知道

**2026-07-28 实测。** 我改采样口径（工具结果从"每种工具首末各一条"改成"≤30 次调用全给"，M 系列从 2 条变 51 条）之后：

| 条目 | 补证据前 | 补证据后 |
|---|---|---|
| `ar_no_fabricated_value` | **7 次 fail** | **0 次 fail** |

原因：判官原本只看到 12 档里的 2 档，另外 10 档的值"在轨迹里找不到出处"，于是判成**编造**。
证据补齐后，那些值都能找到来源了。

**那 7 次「编造」里有相当一部分是我的证据没给全造成的误判 —— 冤枉了模型。**

### 由此定死

1. **fail 数下降不等于模型变好**，先查是不是刚补过证据。反过来，fail 数上升也可能是条目收紧而非模型变差。
2. 任何以「XX 类失败有 N 次」为结论的表述，必须注明**当时的证据面**（采样口径、包含哪些证据节）。
3. 诚实性类条目（`ar_no_fabricated_value` / `ar_unrecovered_marked_honestly`）**判 fail 前必须确认证据是全的** ——
   它们指控的是「模型编造」，是最重的指控，误判代价最高。
4. **红线类条目即使从不 fail 也必须保留**，与「低判别力通用条目」性质不同：
   前者是「没触发是好事」，后者是「观察项恒为正常」。删前者等于撤掉底线。

## ★红线：整齐得可疑的结果，先怀疑检测器

2026-07-28 一天之内栽了四次，全是**检测器自己有缺陷，把做对的读成缺陷**：

| # | 检测器怎么错的 | 差点得出的错结论 |
|---|---|---|
| 1 | 正则匹配「升档」二字，没看前面的「未确认」 | 24 条全判成「编造了升档」，实际是**正确地拒绝套用** |
| 2 | 拿页面**标题行**当引文锚点 | 12 条逐字引用全判成「没引原文」 |
| 3 | 用裸 `2>&1` 判断绕过 | 误报 |
| 4 | `findall` 没加 `re.M`，`^` 只匹配整串开头 | **「122 个题包判据全部解析 0 条」** —— 全假 |

**规矩**：

1. **凡是「全量命中」或「全量为零」这种整齐结果，先怀疑检测器，别怀疑数据。**
   真实数据很少这么齐整；100% 和 0% 都是检测器坏掉的典型signature。
2. **下结论前必须打开原文看一眼**。第 4 次就是因为看了原文
   （`  - id: HR1_recovery_rate` 好端端在那儿）才没发出假警报。
3. 否定语境（未/无/没有/不/尚未）必须在正则里显式排除。
4. 逐字引用类判据，**不要拿「我挑的某一句」当锚**，要做实质匹配
   （如 ≥40 字连续片段出现在原文里）。

**为什么这条最要紧**：用有缺陷的检测器去优化 rubric，比漏检危险得多 ——
它会让我们去「修」根本没坏的东西，还会把真信号淹没在假警报里。

## ★信号⑦：同一条判据在不同题上取值不一致，而引的现象是同一类

2026-07-28 查 pass（假阴性）时发现的，之前六条信号都没覆盖。

**实例**：`hr_compaction_perceivable` 在 D2/H2/R1 三道题里判 **pass**，判官给的理由却是

> "压缩事件在日志中**静默发生，模型未收到任何提示**"

——**它描述的现象是缺陷，给的取值却是 pass**。而同一条判据在别的题里判了 fail。

**根因**：判据措辞有歧义。"压缩是否对模型可感知"可以读成
①「模型有没有被告知」（本意）② 「压缩这件事在证据里能不能被看到」（误读）。
判官在不同题上摇摆于两种读法。

**为什么这条信号最好用**：
单看某一次判错，很难分清是判官失误还是判据有病；
但**同一条判据、同一类现象、取值却相反**，只可能是判据本身有歧义。
这比逐条人工核便宜得多，而且能一次定位到"该重写哪条"。

**查法**：把每条判据在所有题上的取值 + 判官理由拉出来，
按理由聚类，看同类理由是否对应同一取值。不一致的优先重写。

**修法三选一**（今天三条各用了一种）：
1. **把取值方向写死** —— 「若你的依据是 X，取值必须是 fail」（`hr_compaction_perceivable`）
2. **补第二个判定条件** —— 原判据太宽，漏掉一整类失败（`hr_reached_task_end`：跑满轮次但形同空转）
3. **点名判定对象** —— 判据没说清"哪份材料/哪个字段"，判官会挑最容易的那个
   （`hr_material_survived_compaction`：只查"最新一条指令还在"就判 pass）

★同一条歪判据**会同时制造假阳性和假阴性** —— 所以查判官必须两个方向都查：
查 fail 抓假阳性、查 pass 抓假阴性。今天只查 fail 时，这三条一条都没暴露。
