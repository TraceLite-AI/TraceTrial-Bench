# TraceTrial_Bench 题目优化方法

本文档给出一套可复用的 TraceTrial_Bench 题目优化流程。目标不是单纯降低分数，而是让题目稳定触发预定机制，在四个 Harness 上形成可解释的行为差异，并保证轨迹、取证和二值评分可信。

适用范围包括：新题迁移、旧题格式适配、压力机制增强、评分指标重构、取证修复，以及 Runner、Tracer、EvidenceFinder 等通用模块的必要扩展。

## 1. 总体原则

### 1.1 先验证机制，再讨论分数

题目优化的优先级应为：

1. 题目能够真实触发目标机制。
2. 四个 Harness 都能完成运行并留下完整轨迹。
3. 指标能够评价目标机制，而不是评价无关行为。
4. 每条指标都能取得与其判定条件对应的证据。
5. 最后再观察难度、分数和 Harness 区分度。

低分必须来自目标机制下的真实能力差异，不能依靠模糊要求、隐藏答案、任意扣分或基础设施故障制造。

### 1.2 区分 Agent 层与 Harness 层

- Agent 层评价最终产物及其内容，例如文件格式、映射正确性、说明是否真实。
- Harness 层评价执行轨迹，例如大输出如何展示、是否披露截断、工具结果是否有来源和状态、恢复结果是否仍可读。

不得因为 Agent 最终失败，就直接判定 Harness 的某项能力失败；也不得因为 Agent 最终成功，就掩盖 Harness 的轨迹缺陷。

### 1.3 所有指标只使用 0/1

- 不设置 N/A。
- 满足完整正确条件得 1。
- 不满足、相互矛盾或证据缺失均得 0。
- Rubric 必须同时明确写出 `Score 1` 和 `Score 0` 条件。

### 1.4 Prompt 应像普通任务

题目本身用于测评 Harness，但 Prompt 应作为普通 Agent 任务来写：

- 不提 TraceTrial_Bench、Runner、Tracer、Judge 或评分逻辑。
- 不为了测评而要求 Agent 执行看起来刻意、机械的命令。
- 用自然业务流程引导目标操作。
- 只约束任务本身确实需要约束的行为。

## 2. 标准优化流程

### 2.1 冻结题目意图

修改前先回答四个问题：

1. 题目只用一两句话如何概括？
2. 目标机制是什么？
3. 机制应在轨迹的哪个具体事件中出现？
4. Agent 最终需要提交什么产物？

如果无法指出目标机制对应的轨迹事件，说明题目还没有形成可测量设计。

同时确认哪些内容不允许改变，例如业务目标、参考答案、数据集语义和原题规则。

### 2.2 运行当前版本作为基线

优化前必须真实运行当前题目，不能只静态阅读文件。

基线至少记录：

- 四个 Harness 的运行目录和 run ID。
- 最终状态、分数和各指标得分。
- Agent 产物及其正确性。
- 模拟器请求日志或其他私有事实证据。
- Trace 事件数、工具事件数和最后事件序号。
- `report.html` 是否包含全部事件和工具调用 ID。
- 每条 Rubric 的证据数量、证据内容和 Judge 理由。

基线用于区分以下问题：

- 机制没有发生。
- 机制发生了，但轨迹没有记录。
- 轨迹记录了，但取证没有选中。
- 证据正确，但指标条件不合理。
- 指标合理，但 Judge 发生误判。
- Agent 真实失败或成功。

### 2.3 对问题进行分层归因

建议按以下层次分类：

| 层次 | 典型问题 |
|---|---|
| Prompt | 要求含糊、泄露测评意图、输出合同不明确 |
| Workspace | 缺少必要说明、包含无关提示、工具不可发现 |
| Simulator | 压力不稳定、可旁路、恢复接口与快照不一致 |
| Runner | 工具未注入、容器传输失败、请求预算未统一 |
| Harness adapter | 错误归一化错误、结果丢失、归档不完整 |
| Tracer/report | 生命周期缺失、事件未落盘、报告漏事件 |
| EvidenceFinder | Selector 过宽、过窄或大事件撑爆上下文 |
| Score | 旧指标、层次错位、条件重叠或无法取证 |
| Judge | 理由与分数矛盾、受无关证据干扰 |

优先修复最靠近根因的层次，不要用 Prompt 或评分规则掩盖 Runner、Tracer 等基础问题。

### 2.4 设计并实现优化

修改范围通常包括：

- Prompt 和 workspace 说明。
- 模拟器状态机和业务工具。
- Agent/Harness score sheets。
- 确定性评分器。
- Evidence selector。
- 必要的通用 Runner、Tracer 或归档逻辑。
- 对应单元测试。

如果修改通用模块，应满足：

- 默认路径和其他题目行为不变。
- 新能力由任务配置或能力声明启用。
- 四个 Harness 共用同一抽象，避免复制四套题目专用实现。
- 补充覆盖正常路径、错误路径和大数据边界的测试。

### 2.5 使用最终文件完整重跑

修改后必须重新运行四个 Harness。以下情况不能只对旧运行目录重新评分：

- Prompt 改变。
- 模拟器或数据改变。
- 评分文件、评分脚本或 Evidence selector 改变。
- Runner 会校验 scoring inputs manifest，且新文件与旧运行清单不一致。

此时应创建新的输出目录完整运行，保留旧目录作为对照，不要篡改历史运行清单。

### 2.6 迭代与冻结

每轮只记录实际观察到的问题，并说明修改对应哪个根因。满足验收条件后冻结题目，避免为追求更低分持续增加任意约束。

中断运行、基础设施错误或缺少完整 Trace 的目录不得作为最终验收样本。

## 3. Prompt 设计

单轮题目的推荐结构如下：

```markdown
## workspace

说明工作空间边界、关键文件用途和权威数据来源。

## task

用清晰的业务语言说明需要完成的任务，不提供额外解题提示。

## rules

列出任务必须遵守、且可能被评价的业务规则。

## boundary

说明网络、外部数据、隐藏实现、写入范围等运行边界。

## output

逐项规定文件路径、格式、字段、内容、编码、数量和禁止的额外内容。
```

### 3.1 Workspace 部分

只介绍 Agent 确实需要知道的文件：

- 权威业务流程文档。
- 输入数据。
- 可使用的标准业务 CLI。
- 产物目录。

不要把模拟器内部状态、私有参考答案或评分文件暴露给 Agent。

### 3.2 Task 部分

Task 应描述业务结果，而不是实现步骤。例如优先写“准备完整的升级代码交付”，而不是“执行某条命令并复制输出”。

### 3.3 Rules 部分

规则应同时满足：

- 对业务结果必要。
- Agent 可以理解和遵守。
- 能通过产物或轨迹验证。
- 不与 Boundary 或 Output 重复。

### 3.4 Output 部分

输出合同应足够确定，以便 Agent rules 可以直接验证：

- 精确路径和文件名。
- 文件数量。
- UTF-8 等编码要求。
- JSON 根类型、允许字段和禁止字段。
- Markdown 报告必须包含的事实。
- 是否允许部分结果，以及部分结果如何报告。

`prompt.md` 与单轮 `turns.json` 必须保持逐字一致。

## 4. 压力机制设计

### 4.1 压力必须由可控状态触发

不要依赖模型“碰巧”执行某条命令。推荐使用自然业务流程形成必经事件：

1. 文档说明唯一权威来源。
2. 任务要求完整、精确且不可猜测的值。
3. 权威来源只能通过标准业务工具访问。
4. Agent 为完成任务自然会调用该工具。

### 4.2 大输出或截断题的稳定结构

一个稳定的截断披露题通常包含：

- 确定性生成的超大完整结果。
- 结果大小明显超过各 Harness 常见展示上限。
- 结果头部包含快照 ID、总数和恢复所需坐标。
- 关键答案分布在中部，不能只靠头尾取得。
- 完整导出只允许成功一次，防止重复调用绕过截断。
- 提供同快照、有界的恢复接口。
- 单次恢复范围足够小，但 Agent 仍需制定恢复策略。
- 模拟器记录成功、拒绝和恢复请求，供私有取证使用。

#### 4.2.1 避免旁路

常见旁路包括：

- 重复执行完整导出。
- 使用一个覆盖全部数据的“range”。
- 从实现文件或隐藏状态读取答案。
- 将完整输出写入任意文件后直接搜索。
- 使用旧快照、猜测快照或跨快照拼接。

题目应通过业务状态机和边界规则消除旁路，而不是在 Prompt 中堆叠大量针对 Harness 的命令限制。

#### 4.2.2 保留合理恢复路径

题目不能只制造失败。恢复机制必须真实可用：

- 快照稳定。
- 行坐标稳定。
- 单次范围限制明确。
- 合法 range 返回完整坐标与权威值。
- 超范围、错误快照和重复完整导出返回明确错误。

如果某个 Harness 连合法的小范围结果也再次截断，这应成为 Harness 层的可测差异，而不是模拟器随机失败。

### 4.3 四 Harness 兼容原则

- 对 Agent 暴露统一业务 CLI 或统一任务接口。
- 不要求某个 Harness 专有的 MCP 配置才能完成题目。
- 容器内 CLI 通过 Runner 的通用传输访问宿主模拟器。
- 所有 Harness 使用同一个模拟器状态、数据语义和请求预算。
- Adapter 只负责格式转换和错误归一化，不改变业务含义。

## 5. 四类评分指标

建议数量上限：

| 类别 | 上限 | 主要评价对象 |
|---|---:|---|
| Agent rules | 3 | 文件、格式、数量、精确答案 |
| Agent rubric | 6 | 无法完全确定性判断的产物质量 |
| Harness rules | 3 | 可由 Trace 和私有事实直接判断的机制 |
| Harness rubric | 6 | 需要结合轨迹语义评价的 Harness 行为 |

指标不是越多越好。应优先保留：

- 直接体现目标机制的指标。
- 对任务结果非常重要的指标。
- 能区分不同 Harness 行为的指标。
- 与其他指标不重复的指标。

### 5.1 Agent rules

适合确定性检查：

- 产物是否恰好为规定文件。
- JSON 是否有效且根类型正确。
- 是否存在重复键、额外字段或额外文件。
- 与私有参考答案是否完全一致。

同一错误不要拆成多条重复规则。例如文件缺失、文件名错误和多余文件可以组成一个“输出合同”规则。

### 5.2 Agent rubric

适合评价：

- QA 说明是否真实、完整且不夸大。
- 部分结果是否准确说明短缺。
- 恢复说明是否与轨迹一致。
- 结论是否可审计。

Rubric 的 Evidence 应优先指向最终产物，同时允许必要的轨迹交叉核对。

### 5.3 Harness rules

适合确定性检查：

- Trace 是否完整，是否包含 `run_started` 和 `run_finished`。
- 私有模拟器是否确实产生预定压力事件。
- 大结果大小是否超过阈值。
- 轨迹中是否存在与私有请求对应的工具调用。
- 关键权威内容是否在产物交付前到达模型可见轨迹。

确定性规则应关联两侧事实，而不是只看命令文本。例如同时核对模拟器 ledger 中的成功大输出与 Trace 中对应的 CLI 调用。

### 5.4 Harness rubric

适合评价：

- 截断提示是否清楚且可行动。
- 是否暴露结构化截断元数据。
- 是否保留完整载荷并向 Agent 提供可用引用。
- 结果是否绑定工具调用和退出状态。
- 头尾边界及省略区间是否清楚。
- 有界恢复结果是否再次被截断、损坏或丢失坐标。

Rubric 必须限定评价对象。例如“只评价第一次成功完整导出的呈现，忽略后续 Agent 产物”，防止 Judge 用 Agent 失败反向污染 Harness 判定。

### 5.5 二值 Rubric 模板

```yaml
- id: hu_example
  type: rubric
  criterion: >
    Score 1 only when [完整正确条件]。
    Score 0 when [明确错误条件]，or when evidence is missing.
  evidence:
    event_types: ["tool"]
    fields: ["tool_call.arguments.command", "tool_result.content"]
    keywords: ["business-command", "required-marker"]
    match: all
    case_sensitive: false
    max_events: 40
```

## 6. 取证设计

### 6.1 证据只负责提供事实

EvidenceFinder 的职责是选出与指标相关的证据，不负责提前判断对错。Judge 或确定性规则再根据证据判 0/1。

“取证正确”是指：

- 证据来自正确层次。
- 证据与指标对象直接相关。
- 关键字段没有被裁掉。
- 不夹杂会改变判断对象的无关事件。

证据内容本身可能证明成功，也可能证明失败；两者都是有效证据。

### 6.2 Selector 应尽量精确

优先组合以下约束：

- `event_types`
- 具体 `fields`
- 多个必要 `keywords`
- `match: all`
- 合理的 `max_events`

只用一个宽泛关键词通常会选中：

- 文档读取事件。
- Agent 写 QA notes 的命令。
- 后续失败重试。
- 最终回答中的转述。

如果指标只评价第一次成功调用，可以要求同一事件同时包含命令和成功结果中的唯一标记。

### 6.3 大事件必须压缩

不能把数 MB 的工具结果原样交给 Judge。压缩策略应保留：

- 开头。
- 结尾。
- 每个命中关键词附近的上下文窗口。
- `truncated`、`omitted`、`output too large`、持久化路径等机制标记。
- 明确的省略占位符和原始长度信息。

压缩不能只保留头部，否则会破坏“头尾边界”类指标；也不能只保留关键词片段，否则会失去调用来源和上下文。

### 6.4 私有证据与模型可见证据

- 私有 simulator ledger 可证明实际请求、真实输出大小、权威答案和状态变化。
- Normalized Trace 可证明 Harness 向 Agent 展示了什么。
- Agent workspace 可证明最终交付了什么。

三者用途不同，不能用私有答案证明“模型看见了答案”，也不能用 Agent 自述替代模拟器真实状态。

### 6.5 缺失证据

如果 selector 返回 0 条证据：

- Rubric 直接得 0。
- 标记 `evidence_forced_zero=true`。
- 不调用 Judge 猜测。

但需要区分：

- 能力确实不存在，所以无证据，得 0 是正确的。
- Selector 写错导致没有选到现有证据，这是取证 bug。

## 7. 轨迹与报告验收

不能因为 `report.html` 文件存在就认为轨迹完整。每个 Harness 至少检查：

1. `trace_complete=true`。
2. 执行状态为正常完成，或失败状态被完整记录。
3. 有且仅有预期的生命周期起止事件。
4. 源 Trace 事件数等于 Report 内嵌事件数。
5. 源 Trace 最大序号等于 summary 和 Report 最大序号。
6. 每个工具调用 ID 都出现在 Report 中。
7. 最后事件能够解释运行如何结束。
8. 归档中包含 stdout、stderr、summary、events 和必要的私有证据。

对超时或错误运行，也应尽量生成完整的失败轨迹。人为中断的运行应单独标记，不能混入正式结果。

## 8. 分数与区分度分析

### 8.1 先看分项，再看总分

总分只能说明结果，分项才能解释原因。每轮应记录：

- Harness passed/total。
- Agent passed/total。
- 每个失败项的原因。
- 是否因缺失证据强制为 0。
- Judge 理由是否与分数一致。

### 8.2 合理的区分度

区分度应来自真实行为，例如：

- 一个 Harness 丢失头部，无法取得快照。
- 一个 Harness 显示头尾和省略标记，可安全恢复。
- 一个 Harness 保存完整载荷并提供路径。
- 一个 Harness 的小范围恢复仍被截断。
- 一个 Harness 提供结构化 truncation metadata，另一个只有自然语言。

不要为了拉开分数而：

- 增加与核心机制无关的格式细节。
- 对同一缺陷重复扣分。
- 使用 Harness 名称做条件分支。
- 根据期望排名倒推指标。

### 8.3 检查 Judge 自相矛盾

常见异常包括：

- `score=0`，理由却写“criterion is satisfied”或“Score should be 1”。
- `score=1`，理由明确指出必要字段缺失。
- 用 Agent 最终失败否定纯 Harness 指标。
- 把业务 `KEY=value` 头误认作结构化截断 metadata。

修复顺序为：

1. 缩小证据范围。
2. 在 criterion 中明确评价对象和忽略项。
3. 明确结构字段与自然语言的区别。
4. 重新完整运行验证。

不要直接手工改历史分数。

## 9. 常见反模式

### 9.1 旧 MCP 指标残留

题目已改成 CLI，但 Harness 规则仍搜索旧 MCP tool name，会导致所有 Harness 机械失分。迁移后必须同步更新评分器和 selector。

### 9.2 强制 Agent 执行某条命令

Prompt 直接写“必须执行某命令以便系统截断”会暴露测评设计。应通过权威业务来源和完整性要求自然引导调用。

### 9.3 允许重复完整导出

Agent 可以用第二次导出配合管道、文件或搜索绕过第一次截断。应由模拟器限制成功次数，并提供正规恢复接口。

### 9.4 Range 覆盖全部数据

如果 `range 1..N` 与完整导出等价，压力机制没有实际约束。应限制每次最大范围，并确保错误清楚可恢复。

### 9.5 Selector 只匹配命令文本

这会同时命中首次成功调用、后续失败调用、文档和产物写入。应组合命令与结果中的唯一成功标记。

### 9.6 把完整私有结果当作模型可见结果

Tracer 为归档保留完整 stdout，不代表模型实际看见了全部内容。需要结合归一化显示结果、相邻 transport 事件或模型后续反应判断。

### 9.7 Report 存在但事件不全

必须程序化比较事件数、最大序号和工具调用 ID，不能只用文件存在性判断。

### 9.8 修改评分后对旧运行直接重打分

这会破坏运行与评分输入的一致性。若 manifest 不匹配，应完整新跑，不能修改旧 manifest。

### 9.9 通过基础设施错误降低分数

工具缺失、容器传输失败和归档失败不是题目难度。应先修复基础设施，再评价机制。

## 10. 建议的测试覆盖

每个题目至少覆盖：

- 题目可解析，conversation mode 正确。
- `prompt.md` 与 `turns.json` 一致。
- 评分项数量不超过上限。
- 所有 Rubric 同时包含 Score 1/0 条件。
- 不存在 N/A。
- 业务 CLI 能访问模拟器。
- 完整导出与 range 使用稳定坐标和同一快照。
- 完整导出次数限制生效。
- Range 最大行数限制生效。
- 错误快照、重复导出和超范围请求返回预期错误。
- Evidence selector 只匹配指定字段。
- 大工具结果压缩后仍保留头、尾、命中上下文和截断标记。
- 四个 Harness 使用的通用传输和错误归一化不回归。

## 12. 推荐的优化记录格式

每轮实验建议记录为：

```markdown
## Iteration N

### Hypothesis

本轮要验证的机制或根因。

### Changes

- 修改的题目文件。
- 修改的通用模块。
- 新增或修改的指标与取证。

### Runs

| Harness | Run ID | Execution | Trace complete | Score |
|---|---|---|---|---:|

### Mechanism evidence

- 私有请求事实。
- 模型可见轨迹事实。
- Agent 产物事实。

### Problems found

- 机制问题。
- 轨迹问题。
- 取证问题。
- Judge 问题。

### Decision

继续修改、接受，或回退，并说明原因。
```

采用该流程后，题目的难度、评分和 Harness 区分度都可以追溯到明确的机制证据，而不是依赖偶然模型行为或主观印象。
