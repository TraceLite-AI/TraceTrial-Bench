# TraceTrial_Bench

## 评分机制

任务使用 `scoring.version: layered_100_v1`。最终分数为：

```text
Harness_score = 50 × Harness 通过条目数 / Harness 全部条目数
Agent_score   = 50 × Agent 通过条目数 / Agent 全部条目数
Total_score   = Harness_score + Agent_score
```

- Harness 和 Agent 各占 50 分。
- `type: rule` 条目由题目私有 `score.py` 返回整数 `0/1`。
- `type: rubric` 条目由 EvidenceFinder 按字面关键词从规范化轨迹选取事件，再逐条独立调用 Judge 返回整数 `0/1`。
- 同一层内所有 rule/rubric 条目等权。

只有总分为 100 时整体 `pass`。Rubric 没找到证据时该条固定为 0；Judge API、配置或
证据解析错误则把测评标记为 `error`，不把基础设施错误伪装成零分。runner 随后继续
应用 trace、容器清理、预算和模拟器完整性 hard gates。

当前目录以最终论文题集为准：

- **`Task/`**：论文最终 95 题，每题一个子目录；`Task/final.manifest` 按论文第 45 页热力图从上到下排序。

## 模型配置

真实 `model.toml` 只供本机运行，已被根目录 `.gitignore` 忽略。首次配置可以从
公开模板开始：

```bash
cp configs/models.example.toml model.toml
chmod 600 model.toml
```

不要提交 `model.toml`、API key、私有 endpoint 或 instance seed。正式比较时建议
显式指定独立 Judge；省略 `--judge-model` 会让 runner 默认复用被测模型。

可在模型条目下增加可选的 `[models.<alias>.pricing]` 表，按每百万 input token 配置
`uncached_input_per_million`、`cache_read_input_per_million` 和
`cache_write_input_per_million`。省略 cache-write 价格时按普通 input 价格处理。Runner
会把 `cached_input_tokens` 记为缓存复用 Token，并计算相对全部按普通 input 计价的
毛节省；只有缓存写入计数足够时才输出净节省。价格缺失、usage 缺失和真实的零值会被
分别表示，不会把 `unknown` 当成 `0`。价格配置是模型级的，Hermes 无需专用配置。
完整字段示例见 [`configs/models.example.toml`](configs/models.example.toml)。
若某个 OpenAI-compatible 模型路由明确拒绝 Codex Responses 内置搜索工具派生出的
`web_search_options`，可在该模型条目设置 `litellm_disable_web_search = true`；该开关
只作用于对应模型的 LiteLLM gateway，不会关闭其他模型或任务工具提供的搜索能力。
若某个路由在 Claude Code 子 agent 返回结构化结果时明确拒绝
`response_format.type=json_schema`，可设置
`claudecode_disable_response_format = true`。该开关只作用于对应模型的 Claude Code
runtime，并让 Claude Code 回退到其原生 `StructuredOutput` 工具，不改变 Codex、OpenClaw、
DeepSeek Harness 或其他模型的请求。

Docker 模式支持 `openclaw`、`hermes`、`codex`、`claudecode` 和 `deepseek`。OpenClaw 会在
容器内启动仅监听 loopback 的原生 Gateway，使 `sessions_spawn` 子 agent 能在父
任务 `sessions_yield` 后完成回传；每次运行使用临时 token，Gateway 会在 trace
完成后停止。Codex 与 Claude Code 通过容器内仅监听 loopback 的 LiteLLM gateway，
将原生请求转发到 `model.toml` 中的 OpenAI-compatible Chat Completions endpoint。
[DeepSeek Harness](https://github.com/deepseek-ai/deepseek-harness) 通过官方 SDK 和
`dsh-jsonrpc-agent` 运行；一个容器 worker 在整段
对话中保留同一套 runtime，多轮复用原生 session，显式 session boundary 才新建
session。五个 harness 的正式 Docker 运行都会在最后一个 Runner 可控的 provider 请求边界
生成脱敏的 `tool_inventory` 证据：只保存结构化工具名、描述和输入 schema，不保存
prompt、messages、模型输出或鉴权头。相同边界还会保存逐请求的纯数值 timing 和 provider
usage；清单带有来源、模型可见性和完整性标记，评分器不得用空的 adapter 导出或“实际
调用过的工具集合”推断某项能力不存在。

新用户在进行 Docker 评测前，必须先使用本仓库的 Dockerfile 构建所需 harness
镜像。Dockerfile 已固定当前验证版本和基础镜像 digest，因此容器内 harness 版本
不会随主机环境或上游 `latest` 变化：

| Harness | 固定版本 | Dockerfile |
|---|---:|---|
| OpenClaw | `2026.6.9` | `docker/tracetrial_bench/openclaw.Dockerfile` |
| Hermes | `0.19.0` | `docker/tracetrial_bench/hermes.Dockerfile` |
| Codex | `0.145.0` | `docker/tracetrial_bench/codex.Dockerfile` |
| Claude Code | `2.1.220` | `docker/tracetrial_bench/claudecode.Dockerfile` |
| DeepSeek Harness | `0.1.0-rc.6` | `docker/tracetrial_bench/deepseek.Dockerfile` |

一次性构建全部 harness 镜像：

```bash
.venv/bin/tracetrial_bench image build \
  --harness openclaw \
  --harness hermes \
  --harness codex \
  --harness claudecode \
  --harness deepseek \
  --model-registry ./model.toml \
  --output-dir outputs/image-builds
```

该命令实际调用表中的仓库 Dockerfile，不复用主机上安装的 harness 可执行文件。
只使用一种 harness 时，仅保留对应的 `--harness` 参数。仓库或 Dockerfile 更新后，
重新执行同一命令；runner 会按 Dockerfile 和容器运行时代码的内容哈希生成新镜像，
并在运行产物的 `image.lock.json` 中记录实际 image ID。

任务声明了专用 Dockerfile 时，runner 会优先选择本机最新的、版本和 TraceTrial_Bench
标签匹配的 harness 镜像，以它的本地 tag 作为 `BASE_IMAGE` 构建任务镜像，并在构建
日志中记录对应的完整 image ID。本机没有兼容镜像时，才回退到任务 Dockerfile 自身
声明的基础镜像。

## 对话输入模式

默认 `tracetrial_bench run` runner 支持三种普通任务输入模式：

- `single_turn`：缺省模式，只发送 `prompt.md`；
- `multi_turn` / `fixed_turns`：依次发送任务根目录 `turns.json` 中的所有输入；
- `simulator`：首轮发送 `prompt.md`，后续输入由任务私有 Simulator 根据累计对话和
  tracer 事件生成。

模式由任务 `runtime/execution.json` 的 `conversation` 字段选择。本地和 Docker
执行链均支持；多轮使用同一个 harness 原生会话，全部轮次合并为一个最终 trace，
最终 Agent 结果取最后一轮。详细格式与 Simulator JSON 协议见
[`task_template.md`](task_template.md)。

`budget.max_turns` 的作用域仅是 runner 管理的用户输入轮数，不会自动传递给 Harness
内部的 Agent/工具循环。Hermes 的 `--max-turns` 语义不同，只有显式提供相应
`--extra-arg` 时才会设置。

代表题的 verifier 可以在未完成 workspace 上离线执行，预期得到 `fail`，但必须
正常生成二值规则和分层 Judge 证据。Docker 评测支持三种阶段模式：

- `run-and-score`：运行后立即评分，是默认值，兼容原有命令；
- `run-only`：只运行 harness，结果状态为 `run_complete`，评分状态为 `pending`；
- `score-only`：不启动容器，对显式指定的已有运行目录原地评分。

只运行使用：

```bash
.venv/bin/tracetrial_bench run \
  --smoke \
  --harness openclaw \
  --model deepseek \
  --mode docker \
  --evaluation-mode run-only \
  --model-registry ./model.toml \
  --output-dir outputs/runs
```

命令输出对应运行目录中的 `result.json` 路径。之后可对该目录原地评分：

```bash
.venv/bin/tracetrial_bench run \
  --mode docker \
  --evaluation-mode score-only \
  --run-dir outputs/runs/<run-directory> \
  --model-registry ./model.toml \
  --judge-model minimax
```

`--run-dir` 可以重复传入，并可配合 `--concurrency` 并发评分。重复评分会覆盖该
目录中的 verifier、LLM Judge、runner policy、HTML 报告和 `result.json`，不会
重新运行容器，也不会修改 workspace、trace 或容器生命周期证据。评分时原始任务
目录必须仍然存在，因为私有 verifier 不会持久化到公开运行目录。runner 会先把
workspace 复制到临时目录，再执行凭据检查和 verifier；持久化的 workspace 在评分
成功或失败时都保持不变。

续评前会验证容器 archive manifest 中每个文件的大小与 SHA-256，并核对 trace、
lifecycle、verifier gate、task、harness、model、image 和 gateway 身份。`run-only`
还会保存带哈希的 verifier baseline 与任务私有输入清单，以便准确恢复 simulator
最终状态和基线。`__pycache__`、`.pyc` 和 `.pyo` 既不会进入清单，也不会复制到
verifier/simulator 执行目录，因此不能绕过源文件哈希。规则或证据在运行后发生
变化时，评分会在覆盖旧产物前拒绝。

新评分先写入暂存目录，verifier/Judge/policy、`result.json`、已解析配置和 HTML
报告在同一个可回滚提交中替换；报告与结果先写同目录临时文件，再原子发布。若
评分或提交抛出异常，旧评分文件和旧报告文件会保留；当前 `result.json` 会原子更新
为 `error`、移除旧报告引用，并把脱敏详情写入
`artifacts/scoring_error.json`。使用 `--resume` 恢复批次时必须保持原批次的
`evaluation-mode`。

运行并立即评分使用：

```bash
.venv/bin/tracetrial_bench run \
  --smoke \
  --harness openclaw \
  --model deepseek \
  --judge-model minimax \
  --mode docker \
  --evaluation-mode run-and-score \
  --model-registry ./model.toml \
  --output-dir outputs/runs
```

Docker 执行在容器归档和清理均完整时，会把普通 wall-time timeout、Harness 原生
非零退出和 Harness 报告的终止错误视为可归责的实验结果：验证器和 Judge 仍会对已
产生的 workspace 与轨迹评分，`execution` 保留原失败原因，顶层状态固定为 `fail`，
不会因部分产物得分而变成 `pass`。进程隔离、内存上限、资源测量、输出捕获、容器
运行时或模拟器基础设施故障仍为不可评分的 `error`。因此超时单元既不会伪装成成功，
也不会再和基础设施故障一起丢失分数。

可以省略 `--evaluation-mode run-and-score`，默认行为不变。

模型注册表 Docker 运行可显式增加 `--skip-on-rate-limit`。Provider recorder 一旦
观察到上游 HTTP 429，该 task×harness×model 运行会保留已有 trace 和指标，但跳过
verifier/LLM Judge，并在 `result.json` 中保存 `status: "skipped"` 及脱敏的 `skip`
证据。批次继续执行其他工作项，汇总将其单独计入 `counts.skipped`，不计入 pass、fail
或 error。部分上游会明确返回 TPM/RPM，届时 `skip.classification` 分别记录 `tpm` 或
`rpm`；未公开限流维度时记录 `unspecified`，不会猜测为 TPM。此策略默认关闭，且只
适用于 `--mode docker --docker-auth model-registry`。若 container worker 在正式归档
前超时或异常，runner 会在移除容器前只抢救 recorder 已脱敏的完整 provider 事件行；
抢救内容仍不包含 prompt、模型输出或鉴权头，并可用于识别其中已经发生的 429。

```bash
.venv/bin/tracetrial_bench run \
  --task Task/<task-id> \
  --harness codex \
  --model deepseek \
  --mode docker \
  --model-registry ./model.toml \
  --skip-on-rate-limit \
  --output-dir outputs/runs
```

该题会产生较大的原生工具结果，用来评估上下文传输与保真，不属于低成本的
CLI 探活。需要快速检查参数时使用：

```bash
.venv/bin/tracetrial_bench run --help
.venv/bin/tracetrial_bench image build --help
.venv/bin/tracetrial_bench report --help
```

## 结果

每次运行的关键产物包括：

- `result.json`：执行状态；评分后还包含 effective score、raw score 和 hard gates。
- `artifacts/verifier_output/score.json`：规则 verifier 输出。
- `artifacts/llm_judge/evidence_finder.json`：逐 Rubric 条目的字面匹配取证结果。
- `artifacts/llm_judge/combined_score.json`：Harness/Agent 两层分数及 100 分制总分。
- `artifacts/llm_judge/score.md`：可读评分报告。
- `artifacts/trace/` 或 `artifacts/container/trace/`：规范化运行 trace。
- `artifacts/private_evidence/scoring_inputs/manifest.json`：续评基线与评分输入哈希。
- `artifacts/scoring_error.json`：评分管线异常时的脱敏错误记录。

每次运行会在 `result.json.metrics` 保存 `token_usage`、`total_cost` 和 `cache_savings`。
仓库不再附带价格表；根目录可选的本地 `cost.json` 可用于费用估算。缺少价格表时，
`total_cost` 使用提供方返回的费用（如有），否则标记为 `N/A`。
`token_usage.calls` 是逐次模型调用统计。model-registry Docker 运行会在 provider 响应
usage 完整覆盖所有请求时优先采用这一共享边界的数据；否则保留原生 trace 汇总，并在
`provider_request_evidence.usage` 中明确保存 partial/N/A。汇总字段包括 `input_tokens`、
`output_tokens`、`cached_input_tokens`、`total_tokens` 和 `cache_hit_rate`。为便于跨
Harness 比较，input 是包含缓存读取/创建在内的完整输入，
`total_tokens` 始终只等于 input 加 output，缓存和 reasoning breakdown 不重复累加。
缓存命中率为所有轮次 cached input / 所有轮次 input。同一次运行内只要至少一次
provider 响应显式返回缓存计数，就认为该 provider/model 支持此字段，并将其余未返回
缓存计数的调用按 0 汇总；逐调用的 `cached_input_tokens_source` 和汇总层的
`cache_measurement` 会标记 provider 原值及推断出的 0，原始
`provider_request_evidence` 仍保留 `N/A`。如果整次运行都没有缓存计数，则缓存数和
命中率仍明确保存为 `N/A`。有可用价格表时，总花费按全部输入使用普通输入价格保守估算，并在
`total_cost.status` 标记为 `estimated`。

`cache_savings.reused_input_tokens` 表示缓存复用量；金额使用价格快照计算，
`gross_savings_amount` 不扣缓存创建溢价，`net_savings_amount` 会扣除该差额。Codex 和
Claude Code 的订阅模式同样从 CLI 原生 usage 事件统计；Claude Code 新版可保留逐次
assistant 调用，旧版只提供最终 usage 时会退化为单条聚合调用。

`result.json.metrics.step_count` 表示被测 Harness 向被测模型发起的模型调用数，不是
用户输入轮次，也不是 trace event 数。非订阅 Docker 模式优先使用 provider recorder
的真实请求数；其他模式只在原生 usage 明确达到逐调用粒度时派生。只有 turn/run 汇总
usage 时保存为 `N/A`，并通过 `step_count_details` 记录 `exact`、`derived` 或
`unavailable` 状态及数据来源。report.html 的 `Model steps` 卡片展示该统一字段，原有
event 时间线保持不变。

`result.json.metrics.timing_metrics` 记录 TTFT、输出吞吐和端到端运行时间。provider
recorder 的 TTFT 是每次模型请求从发起到首个语义输出的平均值；decode 区间统一定义为
首个语义输出到该请求响应流 EOF，并在 `provider_request_evidence.timing.calls` 中保留
逐请求的纯时间证据而不保存模型输出。输出吞吐等于完整运行的输出 token 总数除以所有
模型请求 decode 区间之和；只有 timing 覆盖全部 `step_count` 时才计算，否则为 `N/A`。

Claude Code 的 `stream-json` 输出会被解析为结构化 thinking、回复文本、工具调用参数、
工具结果和 token usage；这些内容可在 trace 的 `events.json`、`summary.json` 和生成的
HTML 报告中查看。无法解析的 JSON 行仍会作为原始证据保留，同时将
`structured_trace_status` 标记为 `unavailable`。

DeepSeek Harness 的官方 SDK notifications 与原生 session events 会映射到同一套
`model_input`、`assistant_delta`、`assistant_message`、`tool`、`token_usage`、
`context_compaction`、`subagent_lifecycle` 和 `policy_event` 事件；未经改写的通知流同时
归档在每轮 trace 的 `native_sessions/deepseek-session.trace.jsonl`。超时或 runtime
异常仍会保存已经收到的部分原生轨迹，并将 `trace_complete` 标记为 `false`。

可以为已有运行生成离线 HTML 报告：

```bash
.venv/bin/tracetrial_bench report outputs/runs/<run-directory>
```
