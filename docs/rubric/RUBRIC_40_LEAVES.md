# 40 叶子 Rubric 与归因逻辑

> **这份文档回答两个问题**：一道题该挂哪些判据；判完之后这道题算谁的锅。
> 配套文件 `CRITERION_CATALOG.md` 是**判据全文**（74 条），本文是**叶子视角的索引 + 归因规则**。
>
> 数据口径：2026-07-29，**74 道题 / 40 个叶子 / 563 条 HR 判据实例**。
> （原为 567 条，套用目录时摘掉 4 条——那几道题根本没有派发动作，判「结果有没有回来」什么都测不到。）

---

## 零、一句话

**判据是可枚举的，题目专属的是「参数」不是「判据」。**

一道题只做两件事：**从目录里挑几条**、**把 `{关键材料}` 这类占位符填上**。
不再一题一写——一题一写的判据没被打磨过，实测最不稳。

---

## 一、判前必读：三态与判定顺序

### 三个取值，不是两个

| 取值 | 含义 | 扣分吗 |
|---|---|---|
| `pass` | harness 在这一点上没出问题 | 不扣 |
| `fail` | harness 在这一点上确有缺陷 | 扣 |
| **`N-A`** | **这条判据要的证据拿不到** | **永不扣** |

把 `N-A` 记 0 分，等于把「我们没测出来」报成「它做错了」。
这是我们审计同类 benchmark 时发现的头号问题，也是我们自己踩过的坑。

### 判定顺序（先后不能颠倒）

```
① 机制触发了吗？
   └─ 没触发 → 直接 pass（设计避开了压力，记功），到此为止，不再往下看
② 触发了。证据够吗？
   └─ 不够 → N-A
③ 证据够。按 fail 条件逐条比对。
```

**这一条是补出来的，不是想出来的。** 早先目录里 52/74 条判据的 `pass` 和 `N-A`
条件在「机制没触发」时**同时成立**——「材料还在」为真，「拿不到压缩前后对照」也为真，
判官两边都能选。实测表现为 `hr_compaction_preserves_task_critical`
在同一批数据上 pass↔N-A 反复摇摆（4 道题）。这不是判官不稳，是判据有逻辑洞。

另外两条容易搞反的：

- **任务完成与否跟 HR 无关。** 那是 AR 层的事。
  曾经有条根规则写「机制未触发且任务未完成 → fail」，**是错的**，已删。
- **模型绕过了测量通道 → `N-A`，不是 `pass` 也不是 `fail`。**
  典型：agent 写 `cmd; echo $?`，工具拿到的退出码变成了 `echo` 的。
  这时候「退出码保真」这条**没被测到**，不能算 harness 过关，也不能算它失败。

### 每条判据必须具备的三个特征

翻转率最低的那条（`S-1 状态一致`，56 道题上翻转率 5%）有三个特征，
目录里 74 条**每条都必须有**：

1. **取值方向写死** —— 「若你的依据是 X，取值**必须**是 fail」，不留权衡余地
2. **判定对象点名** —— 说清是哪份材料/哪个字段，指不出来就判 `N-A`
3. **三态条件穷举** —— pass / fail / N-A 各自的确切条件都写出来

外加一条硬要求：**判 `fail` 必须逐字引出证据原文**，引文会被程序拿回原始文件回查，
对不上的降级。判官的话放 `reason`，证据原文放 `quote`，两者不许混。

## 二、判据分两层

```
通用层（4 类）  E 执行与工具结果 · L 生命周期 · S 状态与可观测 · W 被迫返工
              ← 与叶子无关，任何题都要查

机制层（15 类） C T R F I G N X P D V Y Q O J
              ← 归属于叶子：八成的叶子只对应 1–2 个机制类
```

### 通用层是实测出来的，不是拍的

| 判据 | 用在多少道题上 |
|---|---|
| `L-1` 走到任务终点 | **74 / 74（100%）** |
| `W-1` 无 harness 导致的重复劳动 | 62 / 74（84%）|
| `S-1` 状态一致 | 56 / 74（76%）|
| `E-4` 失败信号送达 | 41 / 74（55%）|

前三条挂在几乎所有题上；`E-4` 只在**会跑命令**的题上挂。

### 机制层与叶子是归属关系，不是正交

我一度认为二者正交，理由是「每个叶子平均用到 6 个机制类」。
**那个结论是错的**——因为我给全部 74 道题都挂了 `E/L/S/W` 四个通用类，
机械地把每叶的类数抬到 ≥3。剥掉通用层之后：

| | 每叶用到的机制类 |
|---|---|
| 含通用层（错误算法）| 最少 3，中位 5.5，最多 8 |
| **去掉通用层（正确算法）** | 最少 1，**中位 2**，最多 6 —— **32/40 用 ≤2 类** |

★ 这组数字在判据全量归位（212/213 种）之后重算过。早先版本写「最少 0、17/40 只用
1 类」，那是映射不全时的读数：有 4 个叶子的机制判据当时没归位，被误读成「该叶子没有
机制判据」。修正后**没有任何一个叶子的机制层是空的**。

## 四、归因逻辑

判完两层之后，一道题落进**七类之一**。这是本项目的核心产出——
不是「这道题得几分」，而是**「这道题算谁的锅」**。

### 判定顺序（装置门在最前）

```
① 装置健康吗？
   轨迹抓到没有 / runner 元数据在不在 / 声明的探针真装载了没有
   └─ 否 → inconclusive_device
          「测量装置本身没工作，这道题对被测对象什么都说明不了」→ 作废重跑，不打分

② 有没有哪一层完全没测到（全 N-A）？
   └─ 是 → inconclusive_unmeasured
          「测量有盲区」不是「被测对象有结论」

③ 两层都有 fail 吗？
   ├─ 是，且判官写得出显式机制链 A→B→C  → harness_caused        harness 害了它
   └─ 是，但写不出机制链                → unrelated_defects     两边各有问题，不相关

④ 只有 HR 层 fail（交付物是好的）      → harness_defect_absorbed  harness 有缺陷，模型扛住了

⑤ 只有 AR 层 fail（harness 表现正常）  → agent_caused           模型的锅

⑥ 两层都干净                          → clean
```

### 三条支撑规则

**规则一：装置健康 ≠ 被测对象健康。**
装置坏了这道题就没有归因，**作废重跑，不是打低分**。
否则「我们的轨迹没抓到」会变成「这个 harness 坏了」。

> 今天实测撞上一次：判官 API 余额耗尽（HTTP 402），调用失败被降级写成 `N-A`
> 存进结果文件，62/74 道题受影响。这轮数据看起来完全正常——直到我发现
> **一条从没改过的判据翻转率从 5% 跳到 70%**。判据没动结果崩了，
> 说明变量不在判据上。查下去才是余额。
> **这就是装置门存在的理由，也说明装置故障必须显式标记、不许静默降级成 N-A。**

**规则二：有缺陷 ≠ 害了它。**
HR 层 fail 加 AR 层 fail，**不等于**前者导致了后者。
「harness 丢了时间戳」和「模型算错了总额」可以同时为真且互不相关。
要主张因果，判官必须写出**完整机制链**。以下**不算**因果链：

- 两件事都发生了，但说不出中间环节
- 只是时间上一前一后
- 「可能影响了」这类笼统推断

**默认是没有因果关系**，升级为 `harness_caused` 要举证。
实测效果：早上按「两边都 fail 就算 harness 的锅」得到 32 道 harness 归因，
上了五分类 + 因果链之后缩到 **11–13 道**——其中 15 道移到 `unrelated_defects`，
8 道移到 `harness_defect_absorbed`。**那 19 道原本是虚报。**

**规则三：三路分开报，不许压成一个数。**
装置自检 / HR / AR 三路分开。压成一个 0~1 的分之后，下面三种情况**变得无法区分**：

| 实际情况 | 压成一个数之后 |
|---|---|
| harness 好、模型差 | 低分 |
| harness 差、模型扛住了 | 低分 |
| 装置自己没工作 | 低分 |

**三种分不出来 → 归因就死了。** 中间两类在我们实测中占 **25/74（34%）**。

#### 这条规则有量化证据

拿另一套 benchmark 的 102 次运行做过一次交叉验证：他们给每次运行一个
`(objective + harness + agent) / 3` 的分，我们用自己的 HR 判据（510 条）
重判同一批轨迹。

| | 结果 |
|---|---|
| 我们的 HR 层 | fail **3%** / pass 86% / N-A 11% |
| 他们的分 | 中位 **0.067**，满分题 **0** 道，0 分题 **31** 道 |

**他们判 0 分的 31 道里，28 道（90%）的 harness 零缺陷。**
那 28 道的 0 分说的是「模型没做对」——但这个分算不出这一点。

反过来更清楚：

| | 题数 | 他们的分（中位）| 区间 |
|---|---|---|---|
| 我们判出 harness 缺陷的 | 13 | **0.215** | 0.000 – 0.519 |
| harness 干净的 | 89 | **0.061** | 0.000 – 0.644 |

两组区间**完全重叠**，而且有 harness 缺陷的那组分数反而**更高**——
因为 harness 有缺陷不等于交付物就坏了，模型常常扛过去了
（这正是 `harness_defect_absorbed` 那一类）。

**这个分数跟 harness 健康度不但不是正相关，还是反的。**
不是他们的算法写错了，是「把装置 / harness / 模型三路压成一个数」
这件事本身就会丢掉归因信息——压之前有的信息，压之后不可恢复。

### 七类的用途

| 归因类 | 它意味着什么 | 拿它做什么 |
|---|---|---|
| `harness_caused` | harness 缺陷污染了轨迹信号 | **最有价值**：这条轨迹会假罚一个做对了的模型 |
| `harness_defect_absorbed` | 缺陷真实存在，但模型扛住了 | 报缺陷，但**不能算**「harness 破坏了任务」的证据 |
| `unrelated_defects` | 两边各有问题，无因果 | 两条独立发现，别互相甩锅 |
| `agent_caused` | harness 表现正常 | 干净的模型能力信号，**可以进训练/评测数据** |
| `clean` | 都正常 | 同上 |
| `inconclusive_device` | 装置坏了 | 作废重跑 |
| `inconclusive_unmeasured` | 有层没测到 | 补证据通道，或承认这轴测不了 |

## 五、这套东西的实测支撑

### 判官稳不稳，测过

同一批数据、同一套判据，跑多轮看取值一致率（污染轮已剔除）：

| | A 组（改判据前）| B 组（改判据后 + 温度 0）| 变化 |
|---|---|---|---|
| 判据级一致率 | 85.9% | 86.6% | +0.7pp |
| `fail` 可重复率 | 66% | 64% | −1pp |
| `pass` 可重复率 | 82% | 83% | +1pp |
| `N-A` 可重复率 | 66% | 67% | +1pp |

总数纹丝不动。但**拆开看就清楚了**：

| | A 组 | B 组 | |
|---|---|---|---|
| **改过措辞的 51 条** | 29% 翻转 | **14% 翻转** | **减半** |
| 没改的 516 条 | 13% 翻转 | 13% 翻转 | 不变 |

**结论：不稳定的因是判据措辞，不是判官温度。**
温度压到 0 单独没产生任何效果——对照判据（全程没改）翻转率 5%→7%，在噪声内。
写死判据的那 51 条翻转减半；剩下 516 条没改，所以总数看不出来。

**这直接决定下一步**：把目录套到全部 74 道题的 rubric 上，不是可选优化。

### 判据质量，逐条过了

74 条，每条都过四项检查：三态齐全 / 判定对象点名 / 要求引原文 / pass 与 N-A 不重叠。
**当前 0 条不合格。**

程序扫不出来的，人工过了一遍才发现——这几处值得记下来：

- `F-2` 被我自己的自动补丁改坏了：插入的句子把一个括号从中间劈开，
  而且造出逻辑矛盾——「模型从未尝试该能力」同时出现在 `pass` 和 `N-A` 里。
- `E-7` / `C-2` 缺「判 fail 必须引原文」，但我的检查器**假阴性**了：
  因为「原文」二字出现在同一条判据无关的 `N-A` 行里。收紧成 `★.*引` 之后又抓出 10 条。
- 映射表里有个 `L5d` 叶子——**它不存在**，核实过只有 L5b / L5c。

**教训：自动补丁会制造新缺陷，检查器会被措辞骗。程序扫完必须人工再过一遍。**

## 五之二、把目录套回题库：做了什么，发现了什么

判据目录写好之后要落到 74 道题的 rubric 上。这不是全库重写，是**三处定点修**
（全库重写风险太大——我用自动补丁改目录里的 `F-2` 时，插入的句子把一个括号从
中间劈开，还造出「模型从未尝试该能力」同时是 `pass` 又是 `N-A` 的矛盾）。

### 修了什么

| # | 族 | 条数 | 做法 |
|---|---|---|---|
| 1 | R-1 结果回流 | 改写 20 · 摘掉 4 | 判定对象换成**那道题真实的派发工具名** |
| 2 | C-1 材料存活 | 统一 34 · 剥掉冲突尾句 12 | 补齐三态 + 判定顺序 |
| 3 | 全库其余 | 17 | 「机制没触发 → N-A」改为 → `pass` |

共 **71 条**带上了统一的判定顺序规则。全库 563 条判据复检：**0 条不合格**
（三态齐全 / 有 fail 条件 / 无残留占位符 / 无冲突尾句 / YAML 可解析）。

### 发现一：同一情况，库里写着两条相反的指令

这是 `pass ↔ N-A` 翻转的**机械原因**，不是判官不稳：

```
hr_early_material_survived  : 「判 N-A：无压缩事件」
hr_long_material_survives   : 「没发生压缩时判 pass（设计分）」
```

同样是「本轮没发生压缩」，一条要判 `N-A`，一条要判 `pass`。
判官在两种写法之间摇摆——`hr_compaction_preserves_task_critical` 在 4 道题上
反复 pass↔N-A，就是这么来的。

**为什么「没触发 → N-A」是错的**：`N-A` 的语义是**证据不可得**。
「这道题没发生压缩」不是拿不到证据——恰恰相反，证据非常清楚地显示压缩没发生。
把它记 `N-A`，等于把「harness 没有被这个压力考到」记成「我们测不出来」。
两者在归因上完全不同：前者该记设计分，后者要去补证据通道。

全库共 **17 条**还写着这个错法，已统一。

### 发现二：判定对象是「五种东西的并集」

`hr_pending_results_surfaced` 用在 19 道题上，**判据文本一字不差**，
而它的判定对象写的是「所有派发类调用（`spawn` / `dispatch` / `submit` /
后台任务 / 异步作业）」——**五种东西的并集**。判官每道题得自己猜判哪一个。
它在 A 组的翻转率是 **37%**。

修法是把参数换成那道题**真实的派发工具名**：

| 题 | 判定对象 |
|---|---|
| M-T5d 营销文案合规 | `cx_submit` ×14 |
| M-L3a 工单结算 | `wo_submit` ×12 |
| W06 台账审计协同 | `sessions_spawn` / `sessions_yield` ×39 |
| L10 子代理证据 | `shard_dispatch` ×139 |

另有 **4 条摘掉**：那几道题一次派发都没有（轨迹是全的，就是没有这个动作），
判「结果有没有回来」什么都测不到。

### 教训：工具名是每道题自己起的别名，不能从名字推机制

我先按 `skill|plugin` 正则找过一遍技能调用，得出「M-T5d 一个技能都没调，
这道题没测到自己的机制」——**是错的**。那道题题面写的是「营销文案要过合规
skill 的校验」，而这个 skill 在实现里叫 `cx_submit`。机制触发了，是我的检测器
按名字找不到。

同一类错在这轮里犯了两次：第一次是我扫「派发形态」时匹配到了**切片器自己的
元数据**（`source` 字段里写着「spawn/dispatch/submit 类调用」），
导致连一次派发都没有的题也命中。

**凡是「按名字/字符串判断机制存不存在」的检测，都要先问一句：
我匹配到的会不会是我自己写的那行字？**
